# Разбиение Telegram rich message по длине и числу блоков (#6)

## Goal

Отправлять весь текст дайджеста Telegram частями, каждая из которых укладывается в лимиты длины и числа блоков, включая случай одной слишком большой новости.

## Context

- Issue: https://github.com/dmonsoonn/Gorizont/issues/6 и дополнение https://github.com/dmonsoonn/Gorizont/issues/6#issuecomment-6791522538.
- Причина: `_build_telegram_rich_parts` проверяет только длину перед добавлением целой новости; отдельно вынесенная новость повторно не проверяется, подписи частей добавляются после проверки, число вложенных блоков не учитывается.
- Официальный контракт: https://core.telegram.org/bots/api#rich-message-limits — до 32768 символов текста и 500 блоков, включая вложенные блоки, элементы списков, строки таблиц, цитаты и details. Существующий внутренний предел `TELEGRAM_RICH_MESSAGE_LIMIT = 32000` сохраняется; при проверке финальной Markdown-строки учитываются также служебные заголовки и разметка.
- Решение пользователя: слишком большую новость разбивать на продолжения с сохранением всего текста и корректной разметки; учесть оба ограничения и заголовки частей.
- Проверки только локальные, на синтетических данных. Пользователь разрешил добавить регрессии и обновить два существующих теста: строгая граница в `test_long_digest_is_split_between_items` и реалистичный искусственный лимит в `test_messages_are_spaced_to_respect_telegram_rate_limit` с сохранением проверки интервалов.

## Acceptance criteria

1. Given много коротких новостей, которые вместе укладываются в 32000 символов, но превышают 500 блоков When строятся Telegram-сообщения Then дайджест разделён на несколько частей, ни одна часть не превышает 500 блоков с учётом вложенного содержимого и служебных заголовков, все новости сохранены в исходном порядке.
2. Given итоговая часть находится на границе лимита длины или блоков When добавление следующего содержимого превысило бы хотя бы один лимит Then создаётся новая часть; каждая финальная Markdown-строка, включая подпись «Часть N из M», не длиннее `TELEGRAM_RICH_MESSAGE_LIMIT`, включая переход числа частей к двум цифрам.
3. Given одна новость сама превышает лимит длины или 500 блоков When строятся сообщения Then она разбивается на обозначенные продолжения без потери или перестановки текста и ссылок, каждый фрагмент укладывается в оба лимита, details закрыты внутри части, ссылки и экранированные символы не разорваны некорректно.
4. Given несколько профилей и большая новость среди обычных When строятся части Then сохраняются порядок профилей и новостей, исходные номера и оценки; каждая часть с новостью содержит заголовок её профиля, а последующие части имеют корректные номера и общее число частей на языках ru/en/zh.
5. Given короткий дайджест или отсутствие важных новостей When строятся сообщения Then сохраняется прежний результат без лишнего разбиения; для пустого дайджеста остаётся один обзор.
6. Given синтетическая Telegram-конфигурация с конкретным `chat_id` и дайджестом из нескольких частей When сообщения готовятся и отправляются через подменённый транспорт Then все части используют исходный `chat_id` и настройки запроса, получатель не берётся из текста новости, между отправками сохраняется интервал 3 секунды; реальных сетевых вызовов нет.
7. Given данные новостей содержат переносы строк, списки, ссылки, HTML entities, кириллицу и emoji When строятся части Then проверка ограничений учитывает структуру, которая реально отправляется в Telegram, а не только количество внешних `<details>` или число новостей; текст не теряется и разметка остаётся корректной.
8. Given реализация и тесты завершены When выполнены `uv run pytest tests/test_webhook.py tests/test_telegram_rich_limits.py`, `uv run pytest` и `git diff --check`, затем `/verify` и независимый `/review-diff` Then проверки успешны, по AC записаны доказательства, живую доставку и деплой явно отмечено как не проверенные в рамках этой задачи.

## Negative scenarios

- N1: Given одна новость превышает лимит длины или числа блоков даже отдельно When выполняется разбиение Then нет бесконечного цикла, потери остатка новости или отправки заведомо слишком большой части.
- N2: Given много коротких абзацев или элементов списка внутри одной новости When суммарный Markdown короче лимита длины, но блоков больше 500 Then перенос вызывается числом вложенных блоков, а не только внешними details.
- N3: Given ссылка, HTML entity или экранированный символ попадает на границу части When выполняется перенос Then конструкция не разрезается с образованием некорректной разметки и её содержимое сохраняется.
- N4: Given текст новости содержит похожие на настройки поля и чужой `chat_id` When строятся и отправляются части через подменённый транспорт Then исходная конфигурация и получатель не меняются, чужой ресурс не используется.

## Scope

- Change: `src/services/webhook.py` — разбиение и необходимые внутренние помощники Telegram; `tests/test_telegram_rich_limits.py` — новые регрессии; в `tests/test_webhook.py` только два согласованных теста; `docs/configuration.md` — описание разбиения Telegram; этот файл задачи и `.claude/state/`.
- Do NOT touch: общую генерацию текста в `src/ai/`, другие каналы доставки, URL security, конфигурационные модели, `bot/`, workflow, зависимости, пользовательские данные и секреты; остальные существующие тесты. Живая отправка, деплой, коммит, push и закрытие issue в scope не входят.
- Pattern: `_build_telegram_rich_parts`, `_telegram_details` и `_TELEGRAM_PART_LABEL` в `src/services/webhook.py`; `TestTelegramPlatform`, `_make_item` и подмены транспорта в `tests/test_webhook.py`. Сохранить существующий Markdown-контракт `rich_message.markdown`; ограничение числа новостей само по себе не заменяет учёт вложенных блоков.

## Plan

Подтверждена пользователем 2026-11-18.

1. Добавить регрессии на множество коротких новостей, вложенные блоки, одну длинную новость и финальную длину с заголовками; воспроизвести дефект до правки реализации.
2. Внутри Telegram-рендера учитывать консервативный бюджет блоков для формата, генерируемого дайджестом, и длину финальной части; разбивать большую новость на корректно оформленные продолжения без потери текста.
3. Обновить два согласованных теста и описание Telegram в документации; проверить сохранность получателя, порядка и интервалов.
4. Выполнить целевой и полный pytest, `git diff --check`, `/verify` и независимый `/review-diff`; записать Evidence и handoff.

## Knowledge

- Dead ends: none
- Decisions: сохранять весь текст слишком большой новости в продолжениях; внутренний лимит длины 32000; проверять локально без живой отправки.
- Known issues: остальные ограничения rich message (глубина вложенности и медиа) отдельно не расширяют scope этой задачи; материалы обрабатываются в существующем формате дайджеста. Если одна неделимая ссылка или заголовок целиком не помещаются в часть, конструирование сообщений завершается явной ошибкой до отправки; такой элемент невозможно перенести без изменения его представления. Bold/code закрываются и переоткрываются на продолжениях. Консервативный бюджет — три блока на непустую строку генерируемого формата (элемент списка, его контейнер и абзац); переносы внутри длинной новости дополнительно резервируют блоки на каждую строку.
